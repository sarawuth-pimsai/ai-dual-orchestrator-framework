# Dry-run: fictional appointment reminder

This is a tabletop simulation. All actors, approvals, links and evidence below are fictional; no agents were dispatched and no software was built or released.

1. **Requirements:** Business proposes F-001: remind a user of an appointment; acceptance is a single reminder at a user-selected time and no reminder after cancellation. The choice of channel and consent remains OPEN. Founder approval is required before treating the contract as approved.
2. **Handoff:** Business prepares a design-only handoff to Tech with source version, deliverable, criteria, dependencies and gate. State is POSTED / AWAITING RECEIVER; no acknowledgment is assumed. A hypothetical receiver explicitly acknowledges the version and records the open consent dependency.
3. **Architecture:** Tech proposes T3 pending privacy and messaging threat analysis. A design includes time zones, duplicate delivery prevention, cancellation race, data retention, failure handling and recovery. No implementation approval is implied.
4. **Task planning:** DAG: A consent and requirements decision -> B interface and data contract -> C scheduling lane and D user interface lane -> E integration -> F independent review and QA -> G release decision. C and D can run concurrently only after B, with distinct file ownership and real available workers. QA prepares test cases while architecture proceeds. Durations and critical path are unverified without estimates.
5. **Development:** Each lane needs a task contract with scope, owner, dependencies, acceptance, tests and evidence. Application changes remain BLOCKED until Founder explicitly authorizes the defined implementation scope.
6. **QA:** Planned cases cover consent, time zones, duplicates, cancellation races, retry, security and recovery. No tests have run. A successful review and evidence-backed QA sign-off are prerequisites for a release recommendation.
7. **Release:** Founder Go/No-Go, a verified build, resolved critical defects and a rollback plan are required; no release is authorized or performed here.

PM reports the consent decision as OPEN, implementation as blocked, receiver acknowledgment only when evidenced, and the path as provisional. Next owners: Business for the consent proposal, Founder for the decision, Tech for design after actual receipt. No actual Founder action is requested by this fictional scenario.
