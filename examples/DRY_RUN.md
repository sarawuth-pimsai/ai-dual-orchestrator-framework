# Dry-run: fictional appointment reminder

This is a tabletop simulation. All actors, approvals, links and evidence below are fictional; no agents were dispatched and no software was built or released.

1. **Intake:** Founder asks the Requirements role for an appointment reminder. Requirements proposes F-001: a single reminder at a user-selected time and no reminder after cancellation. The choice of channel and consent remains OPEN; Founder approval is required before treating the contract as approved.
2. **Handoff:** Requirements requests UX and consent input from Business, with source version, deliverable, criteria, dependencies and gate. State is POSTED / AWAITING RECEIVER; no acknowledgment is assumed. A hypothetical receiver explicitly acknowledges the version and records the open consent dependency. Business returns its input to Requirements for incorporation and any necessary Founder decision.
3. **Risk and design:** Requirements proposes T3 and the Founder approves the tier pending privacy and messaging threat analysis. Implementation proposes a design and technical choices for Founder approval; the design includes time zones, duplicate delivery prevention, cancellation race, data retention, failure handling and recovery. No implementation approval is implied.
4. **Task planning:** DAG: A consent and requirements decision -> B interface and data contract -> C scheduling lane and D user interface lane -> E integration -> F unit and integration tests, then e2e scripts and Business judgment -> G release decision. C and D can run concurrently only after B, with distinct file ownership and real available workers. Business drafts scenarios and Requirements drafts e2e scripts while design proceeds. Durations and critical path are unverified without estimates.
5. **Development:** Each lane needs a task contract with scope, owner, dependencies, acceptance, tests and evidence. Application changes remain BLOCKED until Founder explicitly authorizes the defined implementation scope.
6. **QA:** Planned cases cover consent, time zones, duplicates, cancellation races, retry, security and recovery. Implementation writes the unit and integration tests, Business writes the user scenarios, and Requirements writes and runs e2e scripts against the environment the Founder names. No tests have run. Evidence-backed results at all three levels are prerequisites for a release recommendation.
7. **Release:** Founder Go/No-Go, a verified build, resolved critical defects and a rollback plan are required; no release is authorized or performed here.

PM reports the consent decision as OPEN, implementation as blocked, receiver acknowledgment only when evidenced, and the path as provisional. Next owners: Requirements for the product contract, Business for consent input, Founder for the decisions, Implementation for design after actual receipt (acknowledged in the record or through a Founder relay). No actual Founder action is requested by this fictional scenario.
